# Scorecard and Indicators Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Code the two rules behind KPI 1, then build rule, domain, account and platform scores with coverage, a
confirmed-only bound and a sensitivity check, eight indicators with daily series and a look-back, and the seven
Check-in 1 KPIs with values, all regenerated by the deliverable notebook and loaded into the store.

**Architecture:**
- **Two rules:** `notebooks/deliverable.ipynb` section 9c gains the two KPI 1 rules (eight register lines appended at
  the end of section 10).
- **Units:** section 10's `finding()` gains two optional arguments that record which units each line marks. The
  register CSV does not change.
- **New section 12, "Scorecard and indicators":** it sits before the run record (which becomes section 13). It turns
  those units into a per-unit outcome table, aggregates it into scores, and computes indicators, look-back and KPIs.
- **Config:** weights, the line mapping and indicator metadata live in a new `config/scorecard.toml`, read through a
  new `SCORECARD_CONFIG` environment variable (default `config/scorecard.toml`).

**Tech Stack:** Python 3.12 / pandas / numpy in Jupyter (headless via `tests/run_notebook.sh`), bash test drivers,
TOML config, DuckDB store. No new dependency (Spearman via `Series.corr(method='spearman')`, which pandas computes
without scipy).

**Spec:** `docs/superpowers/specs/2026-11-10-scorecard-design.md` (read it first; this plan does not repeat its
reasoning).

## Global Constraints

- **Code:** only in `notebooks/deliverable.ipynb`, edited as `.ipynb` JSON (D-037). No helper module. Never touch
  `data/` or `reference/`.
- **Reading:** text first; dates through `to_day`, numbers through `to_number`. No literal record IDs in notebook
  code (section 6's self-check enforces it). Every weight, threshold and target comes from config.
- **Register:**
  - The existing 63 lines stay byte-identical and in place.
  - The eight new lines go after "Correction link points to itself, to a missing ID, or to another account or
    security", in the order of the table below.
  - Every line obeys eligible + not evaluable = population (existing CHECK).
- **Repeated transaction_id on the new row lines:** `apply_copy_rule` as in section 9c (copies with different results
  become not evaluable).
- **Order independence:**
  - Output IDs are content IDs (transaction_id, position_id, key, security_id, …), never row numbers.
  - Every output is sorted by its listed sort columns.
  - Ties in rankings break by `account_id`.
- **Score rounding:** scores and coverage are on a 0–100 scale, rounded **down** to two decimals
  (`floor(x * 100) / 100`) and written with `'{:.2f}'`, so a score with any failing unit never prints as `100.00`.
  This replaces the spec's "one decimal": one decimal could print 99.97 as 100.0. Log it in spec §8. A blank score
  means "nothing evaluable", never 0.
- **Outputs:** `index=False, lineterminator='\n'`, prefix `02_` (so `tests/robustness_test.sh` compares them after
  shuffling).
- **No commits:** the user commits. Each task ends with a checkpoint (tests green, `git status` reviewed).
- **Stop and ask the user** only when:
  - an existing register line or existing output moves;
  - a guide is ambiguous in a way that changes a count;
  - dashboard code would need changing;
  - a test fails that you cannot explain after investigating;
  - the build would deviate from this plan.

  Any other open point: pick the option closest to the spec and log it in the spec's new §8 "Decisions taken while
  building".

## Fixed names (later tasks and tests rely on them)

### New register lines (Task 1)

Stage `master data`, unit `rows`, id kind `transaction_id`, population = all transaction rows.

| # | Name | Status | Rule | Fails when |
|---|---|---|---|---|
| K1 | `Trade on a security_id missing from securities` | confirmed | `TXN_SECURITY_NOT_MASTERED` | security_id blank or not in `securities` |
| K2 | `Trade cusip differs from the security master` | confirmed | `TXN_SECURITY_NOT_MASTERED` | cusip ≠ master cusip. NE: unmastered, or either cusip blank |
| K3 | `Trade currency differs from the security master` | confirmed | `TXN_SECURITY_NOT_MASTERED` | currency ≠ master currency. NE: unmastered, or either side blank |
| K4 | `Trade on an account_id missing from accounts` | confirmed | `ACC_NOT_OPEN_ON_TRADE_DATE` | account_id blank or not in `accounts` |
| K5 | `Trade before the account's open_date` | confirmed | `ACC_NOT_OPEN_ON_TRADE_DATE` | trade day < open day |
| K6 | `Trade after the account's close_date` | confirmed | `ACC_NOT_OPEN_ON_TRADE_DATE` | close day filled and trade day > close day |
| K7 | `Trade on an account closed later, open on the trade date` | cleared | `ACC_NOT_OPEN_ON_TRADE_DATE` | status CLOSED, open day ≤ trade day ≤ close day |
| K8 | `Trade on an account whose status contradicts its close_date` | confirmed | `ACC_NOT_OPEN_ON_TRADE_DATE` | OPEN with a close_date, or CLOSED without one |

- **Not evaluable on K5–K7:** account unknown (K4), trade day unreadable, open_date unreadable, a non-blank
  close_date unreadable, or the account on K8.
- **K5–K7:** one result per row. Precedence: not evaluable, then before open, then after close, then closed later.

Matching rules:
- Every register line matches exactly one `[[lines]]` entry, by exact `finding` or else by the longest matching

  matched line stops the run.
- The `[owners]` table and the KPI targets are checked against `scripts/framework.json`. A KPI target number must
  appear in that KPI's `target` text.

Rule IDs are compared after dropping a trailing ` (added)`. A test's population is every unit of its kind that any of
its scored lines (fail / cleared / not evaluable) looks at. For tests whose lines all share one population, that is
the register's `population`.

### Outcome of one unit in one test

- **Main:**
  - `fail`: any `fail` line marks it;
  - else `not evaluable`: any line lists it as not evaluable, or a `not evaluable` line marks it;
  - else `cleared`: a `cleared` line marks it;
  - else `pass`.
- **Confirmed-only:** the same, with only lines whose register status is `confirmed` able to make it `fail`.
- **Scoring:** passed = pass + cleared; evaluable = passed + fail.

### Output files (column order fixed)

- `02_score_outcomes.csv`:
  - **Rows:** every unit whose main *or* confirmed-only outcome is not `pass` (plain passes are implied: a CHECK
    asserts passed + rows = population per test).
  - **Columns:** `test, domain, rule, unit_kind, record_id, account_id, outcome, confirmed_only_outcome, line`.
  - `line` is the first register line (register order) that decided the outcome.
  - A `transaction_id` unit with copies on two accounts gives one row per account.
  - **Sort:** all columns.
- `02_scorecard.csv`:
  - **Rows:** one per platform, domain, rule and test.
  - **Columns:** `level, domain, rule, test, owner, unit_kind, weight, score, coverage, confirmed_only_score,
    population, evaluable, passed, failed_confirmed, failed_unresolved, cleared, not_evaluable`.
  - Rule and test rows carry their own counts; domain and platform rows leave the count columns blank.
  - **Sort:** level order platform, domain, rule, test; then domain order as in config; then rule, then test.
- `02_scorecard_accounts.csv`:
  - **Rows:** one per non-blank account_id seen anywhere: accounts master, trades, snapshot positions, three_way keys
    and CA holders.
  - **Columns:** `account_id, in_account_master, fund_id, share_class, rank, score, coverage, confirmed_only_score,
    score_nav_proximity, score_weakest_link`, then `<Domain> score`, `<Domain> coverage` for Accounts, Securities,
    Trades, Corporate actions, Positions, Prices, then `fund_nav_result` (`pass` / `fail` / `not evaluable` / `no
    ledger row`).
  - `rank`: 1 = lowest score; ties by account_id; blank when there is no score.
  - **Sort:** `rank` (blank last), then account_id.
- `02_scorecard_sensitivity.csv`:
  - **Rows:** per variant (`nav_proximity`, `weakest_link`, `confirmed_only`) × level (`platform`, `domain`); plus
    per variant an `accounts` row with `worst_n_kept` and `rank_correlation` filled.
  - **Columns:** `variant, level, name, score, main_score, change, worst_n, worst_n_kept, rank_correlation`.
- `02_indicators.csv`:
  - **Rows:** one per indicator I1–I8.
  - **Columns:** `id, indicator, type, status, calculation, refresh, threshold, owner, decision, predicts,
    gaming_note, inputs_needed, value, numerator, denominator, not_evaluable, breaches, first_breach`.
  - Proposed indicators have blank values.
- `02_indicator_series.csv`:
  - **Columns:** `id, key, period, start, numerator, denominator, not_evaluable, value, threshold, breach, partial`.
  - `period` is `day` / `week` / `effective date`; `breach` is `yes` / `no` / `not evaluable`; `partial` is
    `yes` / `no` (weeks only).
  - **Sort:** id, key, period, start.
- `02_indicator_lookback.csv`:
  - **Rows:** one per pair (spec §5.6).
  - **Columns:** `leading, lagging, key_kind, first_breach, lagging_date, lagging_keys, flagged_earlier, misses,
    share_flagged_earlier, earliest_lead_days, median_lead_days, verdict`.
  - `verdict` is `lead shown` / `timing only` / `no lagging problem`.
- `02_kpis.csv`:
  - **Rows:** KPIs 1–7.
  - **Columns:** `n, office, kpi, formula, unit, owner, target, value, numerator, denominator, not_evaluable, met,
    status, source`.
  - `met` is `yes` / `no` / blank; `status` is `computed` / `proposed`.

## Review Focus

The five inputs most likely to bite a user that the spec's own cases don't pin. Each has its test in the owning task:

1. **A trade with a blank security_id** (FXS09): K1 fail, K2/K3 not evaluable. No existing section may crash on it
   or drop it (Task 1).
2. **A register line the mapping does not know**, e.g. a new break class name on another data set: the run stops
   and names the line, never scores silently. Task 2 adds a probe with an unmatched name.
3. **An account seen only in trades** (FXACC9) or only in CA holders: scored, `in_account_master = no`. An account in
   the master with no records gets blank score and coverage, never 100 (Task 4).
4. **A judge changes one weight live:** only platform rows, account scores and sensitivity move. Outcomes, tests,
   rules, domains, indicators and KPIs stay byte-identical (Task 9).
5. **Full-data size:**
   - The outcome table must not hold one row per passing unit, since there are millions of trade rows. Only
     non-pass units are written; passes are counted.
   - The section must add under 90 s to `tests/run_notebook.sh` and stay inside the robustness test's ~4 GB.
   - Measured in Task 10.
