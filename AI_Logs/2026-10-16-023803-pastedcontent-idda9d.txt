     │ 3.2 Three-way reconciliation (rebuild · book · custodian)               │
     │                                                                         │
     │ - Step 1, book vs custodian alone: full outer join of positions and     │
     │   comparison_positions on account + security + as_of_date. On all       │
     │   480,183 keys in both: matched / different. Also 480 only in book, 0   │
     │   only in custodian. This is independent of the rebuild, so             │
     │   rebuild-unevaluable keys still get a book-vs-custodian answer.        │
     │ - Step 2, add the rebuild as the third source: union of all three key   │
     │   sets, with one layer-1 pattern per key:                               │
     │   - all three agree                                                     │
     │   - book is the odd one out                                             │
     │   - custodian is the odd one out                                        │
     │   - rebuild is the odd one out                                          │
     │   - all three differ                                                    │
     │   - one-sided patterns:                                                 │
     │     - book + custodian, no trades (about 384)                           │
     │     - rebuild + book, no custodian (about 480)                          │
     │     - rebuild only, nets to zero (about 42)                             │
     │     - rebuild only, nonzero                                             │
     │   - not evaluable: conflict, blank, or both                             │
     │   - Counts in brackets are notebook 01's. Under the chain they may      │
     │     shift slightly; report what the chain gives.                        │
     │ - Check: the pattern counts must add up exactly to the union. Agreement │
     │   uses quantity_match_tolerance (1e-6).                                 │
     │ - Expectation to test, not assume: the 01 sensitivities suggest the     │
     │   custodian shares the book's duplicate and REVERSED conventions. If    │
     │   so, those keys land in "rebuild is the odd one out", and that is      │
     │   unresolved, not confirmed.                                            │
     │                                                                         │
     │ 3.3 Break classification (layer 2: cause)                               │
     │                                                                         │
     │ - Rules are tested in a fixed order, and the first match sets the main  │
     │   class. Rules and order go in the config and are written before        │
     │   looking at the counts.                                                │
     │ - Each rule is tested on the difference between the odd source and the  │
     │   rebuild. When book = custodian, that is one difference; when all      │
     │   three differ, test book and custodian separately and use the first    │
     │   rule either one meets.                                                │
     │ - Starting set:                                                         │
     │   a. Book counts duplicate copies: book − rebuild = signed quantity of  │
     │      the removed copies                                                 │
     │   b. Book double-offsets REVERSED: book − rebuild = −Σ signed REVERSED  │
     │      quantities on the key                                              │
     │   c. Both 1 and 2: the difference equals their sum                      │
     │   d. Custodian on a settlement-date basis: custodian = the              │
     │      settlement-date rebuild                                            │
     │   e. Unexplained: stays visible                                         │
     │ - Flags (do not change the class):                                      │
     │   - sign conflict (negative-quantity BUY)                               │
     │   - rebook keeps the old gross amount                                   │
     │ - R3 side view: rerun only the 699 reversal keys under R3 and show how  │
     │   their pattern and class move.                                         │
     │ - The builder may add a rule if a large unexplained group appears. Each │
     │   new rule must be written down with its population and be testable.    │
     │                                                                         │
     │ 3.4 The evidenced trace: one negative-quantity BUY                      │
     │                                                                         │
     │ - Selection rule (in config, no IDs): among keys with a sign-conflict   │
     │   flag, present in all three sources and with no other flag, take the   │
     │   first by (account_id, security_id, transaction_id). If no key         │
     │   qualifies, drop the "no other flag" condition and say so.             │
     │ - Hops (Working Guide §4 table, each marked observed or inferred):      │
     │   a. Source: the transactions row as delivered (BUY, quantity −X,       │
     │      gross_amount / price = +X, source_system)                          │
     │   b. Pipeline: the pipeline_events row (timestamps, batch, cutoff). Do  │
     │      other negative quantities cluster in the same source or batch?     │
     │   c. Position: the book equals the raw rebuild with −X; the             │
     │      absolute-value version differs by 2X                               │
     │   d. Custodian: does comparison_positions share the error or not?       │
     │   e. Downstream: the account's fund and share class in ledger_nav.      │
     │      Units misstated, plus an indicative exposure in bps of fund net    │
     │      assets, labelled as exposure, not loss, with the ledger-currency   │
     │      assumption stated.                                                 │
     │ - Control that would catch it: TXN_FIELDS_VALID (quantity > 0;          │
     │   |gross_amount − quantity × price| ≤ 0.01) at trade capture, owned by  │
     │   the Trade operations lead, on fail: reject.                           │

     3.1 Notebook 02 setup and the waterfall

     - Load the ten tables as in notebook 01: DuckDB, all_varchar=true, explicit
       casts, failures kept. Read thresholds and policies from a new

     - Keep a row ledger for every load, filter and join (rows in, rows out,

       → our chain (C7). For each: matched, different, only-in-each-side, not

     - Add the four sensitivities from §2 as one compact table.
     - Assert that the chain reproduces the C7 numbers above.

     3.2 Three-way reconciliation (rebuild · book · custodian)

     - Step 1, book vs custodian alone: full outer join of positions and
       comparison_positions on account + security + as_of_date. On all 480,183
       keys in both: matched / different. Also 480 only in book, 0 only in
       custodian. This is independent of the rebuild, so rebuild-unevaluable
       keys still get a book-vs-custodian answer.
     - Step 2, add the rebuild as the third source: union of all three key sets,
       with one layer-1 pattern per key:
       - all three agree
       - book is the odd one out
       - custodian is the odd one out
       - rebuild is the odd one out
       - all three differ
       - one-sided patterns:
         - book + custodian, no trades (about 384)
         - rebuild + book, no custodian (about 480)
         - rebuild only, nets to zero (about 42)
         - rebuild only, nonzero
       - not evaluable: conflict, blank, or both
       - Counts in brackets are notebook 01's. Under the chain they may shift
         slightly; report what the chain gives.
     - Check: the pattern counts must add up exactly to the union. Agreement
       uses quantity_match_tolerance (1e-6).
     - Expectation to test, not assume: the 01 sensitivities suggest the
       custodian shares the book's duplicate and REVERSED conventions. If so,
       those keys land in "rebuild is the odd one out", and that is unresolved,
       not confirmed.

     3.3 Break classification (layer 2: cause)

     - Rules are tested in a fixed order, and the first match sets the main
       class. Rules and order go in the config and are written before looking at
       the counts.
     - Each rule is tested on the difference between the odd source and the
       rebuild. When book = custodian, that is one difference; when all three
       differ, test book and custodian separately and use the first rule either
       one meets.
     - Starting set:
       a. Book counts duplicate copies: book − rebuild = signed quantity of the
          removed copies
       b. Book double-offsets REVERSED: book − rebuild = −Σ signed REVERSED
          quantities on the key
       c. Both 1 and 2: the difference equals their sum
       d. Custodian on a settlement-date basis: custodian = the settlement-date
          rebuild
       e. Unexplained: stays visible
     - Flags (do not change the class):
       - sign conflict (negative-quantity BUY)
       - rebook keeps the old gross amount
     - R3 side view: rerun only the 699 reversal keys under R3 and show how
       their pattern and class move.
     - The builder may add a rule if a large unexplained group appears. Each new
       rule must be written down with its population and be testable.

     3.4 The evidenced trace: one negative-quantity BUY

     - Selection rule (in config, no IDs): among keys with a sign-conflict flag,
       present in all three sources and with no other flag, take the first by
       (account_id, security_id, transaction_id). If no key qualifies, drop the
       "no other flag" condition and say so.
     - Hops (Working Guide §4 table, each marked observed or inferred):
       a. Source: the transactions row as delivered (BUY, quantity −X,
          gross_amount / price = +X, source_system)
       b. Pipeline: the pipeline_events row (timestamps, batch, cutoff). Do
          other negative quantities cluster in the same source or batch?
       c. Position: the book equals the raw rebuild with −X; the absolute-value
          version differs by 2X
       d. Custodian: does comparison_positions share the error or not?
       e. Downstream: the account's fund and share class in ledger_nav. Units
          misstated, plus an indicative exposure in bps of fund net assets,
          labelled as exposure, not loss, with the ledger-currency assumption
          stated.
     - Control that would catch it: TXN_FIELDS_VALID (quantity > 0;
       |gross_amount − quantity × price| ≤ 0.01) at trade capture, owned by the
       Trade operations lead, on fail: reject.

     3.5 Price and ledger checks

         - |net_assets / shares_outstanding − nav_per_share| ≤ tolerance
         - Set the tolerance from the stored precision of nav_per_share and
           state it in the config before running.
         - Report missing, zero and unparseable inputs separately. Never sum

❯ Should we create a prototype dashboard using Streamlit + Plotly? or are there
  better tools to use?

⏺ Yes, Streamlit + Plotly is the right choice for this project. I'd build it
  after Monday, though: the brief lists the "working executive view" for
  Check-in 3 (week of 9 Nov), not Check-in 2. Before Monday, the catalog
  write-ups, the deck and the dry run come first.

  Why Streamlit + Plotly fits:
  - Same stack as the analysis. It's Python with pandas and DuckDB, added with
    uv add streamlit plotly. Nobody has to learn a new language before the
    final.
  - The figures always match the code. The brief requires that the dashboard's
    numbers agree with the code outputs. If the app only reads outputs/02_* and
    never recomputes anything, that's guaranteed.
  - Drill-down is built in. Clicking a bar on a Plotly chart, or a row in a
    table, can filter the next view. That gives the click path the brief asks
    for: platform → break class → key → the trade, pipeline, position and
    custodian records behind it.
  - Local is enough. uv run streamlit run app/dashboard.py is the whole run
    instruction, and the brief says a local package is sufficient.

  Two cautions:
  - Never deploy it to Streamlit Community Cloud or any public host; the data is
    confidential and the brief forbids it.
  - The drill-down needs record-level outputs. Notebook 02 writes summaries
    today. The per-key table behind the classification (about 480k rows) would
    have to be written to outputs/ as well, for example as Parquet, which is
    already gitignored.

  Alternatives I looked at:
  - Dash (also from Plotly): more control over interactions, but much more code
    for the same result.
  - Power BI: the desktop app doesn't run on macOS.
  - Tableau: the free version (Tableau Public) publishes the data publicly. The
    licensed version breaks the "one command rebuilds everything" chain.
  - Evidence.dev: SQL plus Markdown on DuckDB, nice for report-style pages, but
    it adds a Node toolchain for no gain here.

  For the wireframes of the three office views: the brief asks for layout
  sketches, not software. PowerPoint or Excalidraw is enough, and they can be
  done in parallel with the app.

  When you're ready to start (after Check-in 2), I'd brainstorm it the same way
  we did this plan. The main design question is what the executive sees first;
  the scores and KPIs it would show don't exist yet and belong to Check-in 3.
